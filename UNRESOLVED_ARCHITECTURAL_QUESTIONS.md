## 2. Unresolved Architectural Questions Register

### Question 1: Resolution Strategy for APB Peripheral Address Collision (DEF-ARCH-01)
- **What is Unknown:**  
  In `top/titan_x_top/titan_x_top.v:647`, `psel_uart0` is decoded using a 16-bit prefix:
  `wire psel_uart0 = psel && (paddr[31:16] == 16'h4001 || paddr[31:12] == 20'h40000 || paddr[31:12] == 20'h10000);`  
  This overlaps and collides with all 9 subsequent peripherals assigned to `0x4001_xxxx` (RTC, GPIO, WDT, SPI, I2C, CLINT alias, MMC, QSPI, VDMA). It is unknown whether this was an unintended typo for `paddr[31:12] == 20'h40000` / `20'h40010`, or if UART0 was originally intended to have a dedicated 64 KB window prior to peripheral reallocation.
- **Why it Matters:**  
  Software drivers cannot communicate with GPIO, WDT, SPI, I2C, MMC, QSPI, or VDMA via the `0x4001_xxxx` map because UART0 intercepts all writes and masks read data in `prdata_mux`.
- **Source to be Inspected:**  
  `top/titan_x_top/titan_x_top.v:647-716`, official SoC memory map specification, and bare-metal BSP peripheral header files.
- **Evidence Required to Resolve:**  
  An architectural change decision specifying the exact unique base address for UART0 (e.g., restricting it to `20'h40000`) and affirming the unique address decode ranges for the other 9 peripherals.
- **Evidence Classification:** **CONFIRMED DEFECT in RTL; Resolution Strategy OPEN**.

### Question 2: Watchdog Timer Reset Action & System Reset Propagation (DEF-ARCH-02)
- **What is Unknown:**  
  In `top/titan_x_top/titan_x_top.v:1036-1042`, signal `wdt_reset_n` is generated by `watchdog_timer.v`, but has **zero sink load** in `titan_x_top.v`. It is unknown how watchdog hardware reset was intended to interface with the system reset tree: whether it should assert `core_rst_n`, trigger an external reset supervisor pin, or enter the secure boot gating logic.
- **Why it Matters:**  
  Watchdog expiration currently generates only an interrupt (`plic_irq[14]`). If a core suffers a hard lockup or bus deadlock, software interrupt servicing is impossible, leaving the hardware permanently frozen.
- **Source to be Inspected:**  
  `top/titan_x_top/titan_x_top.v:97-98, 1036-1042`, system reset controller specification, and board-level power management guidelines.
- **Evidence Required to Resolve:**  
  Architectural definition of the reset tree: whether `core_rst_n` should be redefined as `rst_n & boot_pass & wdt_reset_n`, or if `wdt_reset_n` should drive an external chip-level pad.
- **Evidence Classification:** **CONFIRMED DEFECT in RTL; Reset Tree Intent OPEN**.

### Question 3: Level 2 Cache Capacity Target & Silicon Physical Strategy (DEF-ARCH-03 / 04)
- **What is Unknown:**  
  While `includes/params.vh:57` specifies `L2_SETS = 2048` (2 MB capacity), the actual synthesized hardware implements `SETS = 64` (64 KB capacity) using behavioral standard-cell register arrays (`l2_cache_ctrl.v:112-118`). It is unknown whether the 64 KB capacity was an intentional compromise to permit rapid ASIC logic synthesis without memory compiler licensing, or an unparameterized placeholder meant to be upgraded to 512 KB / 2 MB.
- **Why it Matters:**  
  A 64 KB shared L2 cache across 4 RV64 cores causes severe cache thrashing on multi-threaded workloads. Conversely, synthesizing 2 MB out of standard-cell flip-flops would require over 16 million logic gates and fail place-and-route.
- **Source to be Inspected:**  
  `includes/params.vh`, `memory/l2_cache_ctrl/l2_cache_ctrl.v`, `synth_titan_x.tcl`, and SCL 180nm physical floorplan / memory macro availability.
- **Evidence Required to Resolve:**  
  Foundry memory compiler macro availability (e.g. SCL 180nm SRAM blocks) and a management decision on whether TITAN-X tapeout targets 64 KB (flip-flop based) or multi-banked SRAM macros (512 KB – 2 MB).
- **Evidence Classification:** **HIGH-CONFIDENCE Parameter Mismatch; Physical Strategy OPEN**.

### Question 4: Product Roadmap for RV64GC Application Core Extensions (DEF-ARCH-05)
- **What is Unknown:**  
  Repository documentation, commit messages, and master README claim "RV64GC Heterogeneous Multicore". However, direct RTL verification confirms that Atomics (A) is unimplemented, FPU (F/D) is unintegrated, Compressed (C) is trapped as illegal, MMU Sv39 is unintegrated, and Privileged Architecture is strictly Machine-mode (M-mode). It is unknown whether TITAN-X Phase 1 was formally redefined as a bare-metal microcontroller (RV64IM_Zicsr), with RV64GC deferred to Phase 2.
- **Why it Matters:**  
  Software compatibility: RV64GC is required to boot standard Linux (e.g. Debian, Fedora). RV64IM can only execute bare-metal RTOS or embedded control loops.
- **Source to be Inspected:**  
  `SMVDU_TITAN_X_ASIC_Implementation_Roadmap.pdf`, project charter, and tapeout qualification criteria.
- **Evidence Required to Resolve:**  
  Official signoff document specifying whether Phase 1 tapeout target is explicitly RV64IM M-mode, and detailing the integration schedule for FPU, MMU, and Atomics.
- **Evidence Classification:** **CONFIRMED Implementation Reality; Product Intent OPEN**.

### Question 5: Formal Toolchain Reproduction Blockage
- **What is Unknown:**  
  Extensive formal test suites and SystemVerilog Assertions (SVA) exist in `formal/` and `verification/formal/`, but the SymbiYosys (`sby`) driver is absent from the host system PATH. It is unknown what solver engine (Z3, Boolector, Yices2) was utilized during original formal signoff.
- **Why it Matters:**  
  Independent verification of formal mathematical proofs cannot be executed natively on this host until tool dependencies are provisioned.
- **Source to be Inspected:**  
  `verification/formal/`, `formal/scripts/`, and environment configuration scripts.
- **Evidence Required to Resolve:**  
  Provisioning of `sby` and underlying SMT solvers in the host environment, followed by reproduction of formal test suites.
- **Evidence Classification:** **BLOCKED (Toolchain Dependency Unavailable)**.
